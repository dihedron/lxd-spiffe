# Operational guidance

The rules below gather, in one place, what the design and the lab's measurements require of a deployment. The other chapters and the *Setup Guide* explain each in context. Threat IDs refer to *Architecture and Design*.

1. **A dedicated LXD identity and group for SPIRE**, with only the grants of its proof mode, in the SPIRE-managed projects: project `can_view` (granted first: LXD refuses every other grant in a project the group cannot view) and project `can_view_instances` on each allowed project, plus the instance grant of the mode, spread over several groups of at most 90 instance grants once the instances outgrow one (a group holds at most 99 permissions). Never a server administrator credential (`T10`).
2. **Dedicated projects** for SPIRE-managed instances; with `config_push`, restricted projects (`restricted=true`), which keep `can_edit` from reaching the host. A narrow challenge broker would be the recommended pattern for highly sensitive environments, in either mode, but it does not exist yet: until then, rely on dedicated identities, restricted projects and `file_pull`.
3. **Prefer `file_pull`.** Do not mount shared storage at, above or below the proof directory (`/run/spire/lxd`, and so `/run`) in instances: the server refuses such instances (`T2`).
4. **Run SPIRE Agent as root**; do not open `/dev/lxd/sock` to other users; set `security.devlxd=false` on instances that need neither devLXD nor `config_push` (`T13`).
5. **Restrict who can edit** profiles, `user.*` keys, image properties and network attachments of everything your registration entries rely on (`T9`).
6. **Pin the LXD server certificate's fingerprint.** Rotate SPIRE's client certificate regularly, or on LXD 6.x use a bearer token issued with an explicit short expiry (the default is 10 years); a new token revokes the previous one at once, so the job that issues it must write the token file atomically right after issuing, and that job holds identity-management rights: short-lived tokens move the long-lived privilege rather than remove it. Keep `server_id` unique across all LXD servers and clusters (`T5`, `T7`).
7. **Use a short agent SVID lifetime** (one hour or less); consider `reattest = "deny"`; on restore, rollback or decommissioning, evict the agent and remove its entries (`T14`). A copy or restore that inherits `/var/lib/spire/agent` is the original's node: its agent never attests and its workloads get the original's workload SVIDs. Evict the original's agent when you copy or restore an instance that runs one, or remove the agent's data before the copy first starts. Agents of this attestor attest again at about half their SVID's life (measured: 6 agents with 5-minute SVIDs, 29 attestations in 12 minutes), so a short lifetime bounds how long such a copy passes for the original; the copy case itself was not timed. Keeping the agent's data on a tmpfs is a mitigation under evaluation, at the cost of an attestation at every boot.
8. **Firewall** SPIRE Server's endpoint to the instance networks, and the LXD API to SPIRE Server and the administrators (`T11`).
9. **Audit LXD's lifecycle events** requested by the SPIRE identity that touch anything other than `user.spire.challenge.*` or read operations.
10. **VMs: start SPIRE Agent after `lxd-agent`**, which serves the files API and devLXD in a VM: systemd `Wants=lxd-agent.service` and `After=lxd-agent.service`; OpenRC `depend() { after lxd-agent; }`. After a cold boot, `lxd-agent` answered in 16 to 27 seconds on Debian, Alpine and Ubuntu, and in 30 to 72 seconds on Rocky Linux and AlmaLinux 9. Where the order cannot be set, raise `proof_timeout` for VMs (90 seconds is indicative).
11. **RHEL 9 derivatives with SELinux enforcing**: without a policy for it, `lxd-agent` cannot start and neither proof mode works. Install the drop-in `/etc/systemd/system/lxd-agent.service.d/selinux.conf` with `[Service]` and `ExecStartPre=/usr/bin/chcon -t bin_t /run/lxd_agent/lxd-agent`; check with `ps -eZ | grep lxd-agent`.
12. **Clusters**: one `servers` entry per cluster, its `url` on a load balancer or virtual address if attestation must survive a member being down. The `member` selector states where the instance ran when it attested, not where it runs now. After a VM's evacuation, its attestations may fail for about 30 seconds while `lxd-agent` starts; the agent retries. Live migration is untested. For per-group policy, use projects with `restricted.cluster.groups`: there is no cluster-group selector.
13. **LXD daemon crashes**: LXD restarts every container of the server (VMs keep running), and lifecycle operations in flight are lost, which can leave an instance stopped. Every container's agent then attests again at about the same time: size the server's `limits` for the containers of one LXD server, or expect their attestations to queue for a while. `snap restart lxd` is not a daemon restart: it stops and restarts every instance on the server; plan it as maintenance.
14. **Orphaned challenge keys** (`config_push`): an attestation whose cleanup could not run leaves its `user.spire.challenge.<id>` on the instance; harmless, and removed by the instance's next `config_push` attestation. Remove those of instances that will not attest again by hand (*Routine procedures*). On a cluster, a challenge write forwarded by a member can fail and still have been applied; the key then stays until the next attestation.
15. **Cluster maintenance**: do not evacuate a member whose containers may attest with `file_pull` (the evacuation can fail and leave a volume that needs a manual repair, *Incident procedures*); with `config_push`, an evacuation can fail with `Instance is busy running a "update" operation` and be repeated; on LXD 6.9 an evacuated member loses its database role, so do not touch a second member until the first is restored; a power-off can empty a member's image cache. After every evacuation, check that the volumes left the member before restoring it.
16. **Agent timeouts**: `attestation_timeout` (default 30 seconds) bounds one attestation on the agent; `proof_timeout` (default 15 seconds) is how long the proof stays. Keep the agent's `proof_timeout` at least the server's, and `attestation_timeout` longer than `proof_timeout` plus a few seconds. For VMs whose agent cannot start after `lxd-agent`, with the server at 90 seconds: `proof_timeout = "90s"`, `attestation_timeout = "2m"`.
17. **SPIRE does not restart a crashed plugin.** SPIRE Server 1.15.5 keeps running when the `lxd-server-plugin` process dies (killed three times in the soak, never restarted): every attestation then fails, and agents whose SVID expires cannot attest again. Only a restart of SPIRE Server brings the plugin back, and supervising SPIRE Server's process does not help, since it stays up. Alert on `plugin process exited` in its log, or on `Nodeattestor(lxd_iid): connection error`.
18. **Many agents behind one address**: SPIRE Server rate-limits attestations per source address (`ratelimit { attestation }`, one a second by default) before any plugin runs. Containers behind one NAT bridge share an address, so a mass restart queues them: with 100 agents the last waits about 100 seconds. Set the agents' `attestation_timeout` longer than the longest wait (the lab used `4m` for 100 agents; with the default 30 seconds only 41 of 100 attested), or turn the rate limit off, or give the agents separate addresses.
