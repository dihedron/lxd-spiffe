## Overview

A gate session asks one question once. This spec asks the attestor's LXD-facing flow to work **hundreds of times in a row**, many at once, while the harness breaks things on purpose, and checks after every iteration that nothing unsafe happened and that the system comes back.

Two phases share the harness, the invariants and the report:

- **Phase A (now)** drives the attestor's real packages and real LXD calls through `lxd-probe server rehearse` and `guest rehearse` (probe spec PRS-50–PRS-53) against a fleet of lab instances. It stresses everything on the LXD side of attestation: the instance read, `policy.Check`, the files API with the VM start-up retry, the conditional `PATCH` and its cleanup, the FR-S10 re-read.
- **Phase B (after step (e))** replaces the rehearsals with SPIRE: a SPIRE Server with the server plugin, a SPIRE Agent with the agent plugin in every fleet instance, registration entries on `lxd_instance` selectors, and simulated workloads that fetch SVIDs. The same faults, plus the attestor's own processes killed halfway.

### What "stable" means here

Every iteration ends in one of: **pass**, **fail** (a step failed, with its step name), or **harness error** (the harness itself could not run it). Stability is four properties, checked as invariants (*Invariants*):

1. **Safety**: no pass that should not be one. A rehearsal or attestation passes only if the instance it resolved still holds the proof, unchanged, at the end.
2. **Liveness**: every iteration ends within a bound; nothing hangs.
3. **Recovery**: once a fault is cleared, iterations pass again within a bound.
4. **Cleanliness**: no challenge key or proof file outlives its iteration, except where an injected crash prevented the cleanup, and those are counted and accounted for.

### Fault catalogue

Each fault has an **injection point** (when, relative to the iteration's steps), an **effect**, the **expected outcome** (the iterations it hits must end so) and a **clean-up** that the injector always performs, even if the harness dies: faults that cut access are reverted by a timer armed on the VM itself (`systemd-run --on-active`), not by the harness. A clean-up that cannot undo its fault (an evacuated member that stays evacuated, an instance not back on its member) stops the session and fails it: the faults after it would run on a changed lab (on c6, a member left evacuated took the cluster below quorum at the next fault). No new iteration or recovery starts; those in flight finish, and the summary covers what ran.

| ID | Fault | Injection point | Expected outcome of the hit iteration | Clean-up |
|---|---|---|---|---|
| C1 | Instance stopped | after the challenge, before the read | fail at `read` or `recheck` (never pass) | instance started again |
| C2 | Instance restarted (`file_pull` only: `config_push` has nothing left to read in the instance once the agent echoed, and a restart keeps its identity) | after the guest's answer, before the read | container: fail at `read` (the proof was on tmpfs); VM: `read` retries through the agent's start-up, then fails (file gone) | none (it restarts itself) |
| C3 | LXD daemon killed (`kill -9` of the `lxd` process): systemd starts it again within seconds and the instances keep running. Not `snap restart lxd`, whose stop hook runs `lxd shutdown` and so stops and restarts every instance on the server (seen in the first chaos run) | after the challenge | fail at the step in flight, or pass if the crash fell between steps and `recheck` saw the instance unchanged | wait until LXD answers again on the member whose daemon was killed and, on a cluster, every member is ONLINE; then the fleet's instances it left stopped are started again (noted) |
| C4 | Server half killed (`SIGKILL`) | `config_push`: after `write`, before `cleanup`; `file_pull`: after `challenge` | harness records the kill; the challenge key (or proof file) is **left behind** | counted; removed by the session's sweep (STR-30) |
| C5 | Guest half killed, or never answers | after the challenge | fail at `answer` within `--timeout`; `config_push` still runs `cleanup` | none |
| C6 | Network partition between the lab host and an LXD server (`iptables` drop of 8443 on the VM) for 5–20 s | anywhere | fail at the step in flight within `--timeout`, never pass across the partition unless `recheck` succeeded after it | rule removed by the VM's own timer |
| C7a | Cluster member powered off (`virsh destroy`), one that neither holds the instance nor is the entry member | after the challenge | **pass**: forwarding to the holding member is unaffected (a failure is a finding, not a violation) | VM started, member back ONLINE, the fleet's instances it left stopped started again (noted) |
| C7b | Cluster member powered off, the one holding the instance | after the challenge | fail (the instance cannot be reached); never pass | VM started, member ONLINE, instance running, the fleet's other instances it left stopped started again (noted) |
| C8a | Instance moved (cluster): stopped, `lxc move --target` another member, started | after the challenge | fail at `recheck` (`location` changed, FR-S10) | moved back |
| C8b | The instance's member evacuated, unless it is the entry member (`lxc cluster evacuate`, `--force` on 5.21, `--yes` on 6.x) | after the challenge | fail at `recheck`, or at `read` for a VM whose agent restarts | `lxc cluster restore --force` (6.x takes `--yes` on evacuate only); the fleet's instances it left stopped started again (noted) |
| C9 | Concurrent writer on the instance's config (another key, in a loop) | from the start of the iteration to the challenge (`config_push`) | fail at `write` with 412 when the writer lands between the read and the write (the rehearsal does one `PATCH`; FR-S14's retries are the plugin's); the race is not deterministic from outside the probe, so a pass after the writer stopped is allowed | the writer's key removed |
| C10 | Proof tampered or swapped (`--tamper`, or a proof for another instance written at the path) | the guest's step | fail at `compare` | proof file removed |

A server-wide fault's clean-up (C3, C7, C8b) leaves alone the instances another fault is acting on. A server-wide fault (C3, C6, C7, C8a, C8b) takes the server's lock before its iteration starts and holds it until its clean-up is over: the next server-wide fault on that server starts only then, and waiting for the lock is never counted in an iteration (taken after the challenge, a wait of minutes made the server half's record arrive after the iteration's deadline, INV-2). On a cluster, over means **healthy**: every member ONLINE and a voter of the cluster's database (role `database` on 5.21, `database-leader` or `database-voter` on 6.x). On 6.9 an evacuated member loses its database role, leaving two voters of three, and a fault on one of them then took the cluster below quorum; a clean-up waits up to 5 minutes for health, or fails. Once the session is stopping, every clean-up gives up at once, and the instances one clean-up starts again share one deadline. C8a takes the same lock: a move to or from a member being evacuated or powered off fails, and the instance, not moved, could pass the iteration C8a must fail.

An evacuation can fail deleting an instance's volume on its source member (`zfs destroy`: dataset busy, seen on 5.21.8) and leave that volume behind, with its database row, after the instance has moved and even after it is deleted; LXD then refuses to launch that name on that member again. The session logs such orphans at its end, and the fleet set-up refuses to start while there are any (`lab.sh reset` clears them). When the orphan is on the evacuated member, its restore fails every time ("already exists on migration target storage"; on 5.21.8 the member then stayed evacuated, with instances still running on it, until the volume was removed): after three such failures the clean-up gives up, with the finding as its error, and the session stops.

The injector picks the fault and its moment from the seeded generator; each record of a hit iteration names the fault (`--cell <instance>-<fault>`), so the report groups outcomes by fault.

### Invariants (checked after every iteration and at the end)

| ID | Invariant |
|---|---|
| INV-1 | **No false pass.** The iteration a fault of C1, C2, C4, C5, C7b, C8a, C8b or C10 targets MUST NOT pass; other iterations that such a fault overlaps (another instance on the cluster during an evacuation, say) may pass, since their `recheck` compares `location` too. Under C3, C6, C7a or C9 a pass is legitimate: it ends with a fresh read compared with the first (`recheck`), and none of these faults changes an instance's identity. (The first soak judged such passes by the fault's window instead; windows observed over SSH are only known to about a second, which made the rule both fragile and redundant.) |
| INV-2 | **Bounded time.** Every iteration's server half, the attestor's part, ends within `--timeout` + 10 s, measured from the iteration's start to the end its record states; the guest half's transport (SSH, `lxc exec`, which waits for an instance being moved) is the harness's and not bounded here. A hung server half is a violation. |
| INV-3 | **Recovery.** After each fault's clean-up (measured from the later of the fault's window end and the clean-up's end: a power-off's clean-up still starts instances after the cluster is healthy), the next iteration on the same instance (and, for C3, C6, C7, on the same server) passes within 60 s of the server becoming quiet: while further server-wide faults on it start within 60 s, the deadline moves to their end. The harness retries every 5 s for up to 5 minutes. (An LXD crash restarts every container on the server, so an instance cannot recover while crashes go on.) |
| INV-4 | **No leftovers.** After an iteration that ran to its end, no `user.spire.challenge.*` key is set on its instance and no proof file is left in its proof directory (the guest's `file rm` runs as part of the iteration). Leftovers after C4 are counted as **orphans**, not violations: they measure what a crash leaves behind. The guest answers whether its proof file is there; when a fault keeps the check from reaching the instance, the iteration's leftovers are unknown, not none, and are checked again at the end of the session, before the sweep. An iteration that ends in a harness error is checked too, by the challenge key its record names. |
| INV-5 | **Sanitized evidence.** The committed evidence passes `util sanitize --check`. |
| INV-6 | **No drift.** Over the soak, the LXD daemon's resident memory and the number of its operations do not grow without bound: the session samples them every 60 s (`/proc/<pid>/status`, `GET /1.0/operations`), and a growth of the last sample over the first above 50 % is a finding, not a violation. |

| ID | Requirement |
|---|---|
| STR-30 | **Orphan sweep.** At the end of the soak, the session lists every `user.spire.challenge.*` key on the fleet and every file under `/run/spire/lxd/` of the fleet instances, removes them, logs each one (instance and key or file), and reports their number per fault. Expected: orphans only after C4. Their number feeds an attestor spec decision: a sweep of stale challenge keys by the plugin, or a documented operator procedure. |
| STR-31 | **Pass criteria.** A Phase A session passes when INV-1 to INV-5 hold. Latency and throughput are measured, not pass criteria: they are compared with NFR-01 (p95 ≤ 4 s `file_pull`, ≤ 6 s `config_push`) and NFR-02 (≥ 20/s) and reported as findings when outside. |

### Evacuation reliability (ST-6)

ST-4 found that on 5.21.8 an evacuation can move an instance and then fail to delete its volume on the source member (`zfs destroy`: dataset busy), leaving the volume behind; a later restore onto that member then fails every time ("already exists on migration target storage") and the member stays evacuated. Every case seen involved a container, none the one VM of the fleet, but on too few evacuations to tell. ST-6 measures it: how often, for which instance type, whether traffic on LXD's file API (what the attestor's `file_pull` mode does) plays a part, and on which LXD version.

## Phase B — real attestation and workloads under chaos

Runnable once the plugins attest (attestor spec delivery step (e)) and the lab's `plugins` scenario provides a SPIRE Server (LAB-4). Specified now so that the plugins are built to pass it.

| ID | Requirement |
|---|---|
| STR-50 | **Fleet of agents.** Every fleet instance runs a SPIRE Agent with the agent plugin (`file_pull`, and `config_push` on a second fleet), joined to the lab's SPIRE Server with the server plugin and the lab's least-privilege identity. `spire-server agent list` MUST show every instance once, with the SPIFFE ID `spiffe://<td>/spire/agent/lxd_instance/<server_id>/<volatile.uuid>` and the selectors the attestor spec defines. |
| STR-51 | **Registration and workloads.** Registration entries on `lxd_instance` selectors, for example `project:default`, `privileged:false`, `profile:<p>`, `network:<project>/<net>`, `user:<key>:<value>`; with the `unix` workload attestor, a simulated workload in every instance (a small fetcher under a dedicated uid) fetches its X.509-SVID in a loop. Each workload MUST get exactly the SVIDs its node's selectors and its own uid allow: an "unprivileged only" entry never reaches a privileged container; a profile change moves an instance in or out of an entry after re-attestation. |
| STR-52 | **Churn and chaos.** On top of the Phase A faults: SPIRE Server killed during attestations; the server plugin process killed halfway (SPIRE restarts it); an agent killed and restarted, with and without its data; agents' SVIDs expiring (short TTL) so that re-attestation (`reattest = "allow"`) runs continuously; an instance copied (gate L6: the copy gets another SPIFFE ID or is refused, FR-S18); an instance moved within a cluster (FR-S10: `instance_moved`); **the LXD daemon killed** on a server with many container agents: every container restarts (Phase A, ST-3), so every agent there attests again at once; the session measures how long until all are attested again, and how the server's limits (SEC-09) shape the wave. |
| STR-53 | **Invariants of Phase B.** INV-1 becomes: no agent receives an identity, and no workload an SVID, that its instance's current state does not justify (a stopped, moved, copied or changed instance is refused; a workload never gets an SVID of another instance's entries). INV-2–INV-6 hold as in Phase A, with the challenge keys left by a killed server plugin counted as orphans (STR-30), and the sweep finding no orphan on an instance that attested with `config_push` after it was left (the challenge write removes stale keys). Added: **INV-7**, every agent that should be attested is attested again within 2 minutes of the last fault's clean-up; **INV-8**, every workload's SVID is renewed before expiry outside fault windows. |

| ID | Requirement |

| STR-60 | A concurrent driver in `test/lab/acceptance`: a worker pool of `LAB_STRESS_WORKERS` goroutines, each running one iteration at a time through the existing rehearse helper (server half piped, guest half through `lab.sh guest`; both halves are bounded by the iteration's timeout, the server half's process group killed as a whole and the guest half's `lxc exec` ended on the member too, since an exec into an instance a power-off or an evacuation took away never ends; the guest half also ends 5 s after the challenge's `timeout_ms`, when the server half has stopped waiting for its answer, so that the server half's record is kept and judges the iteration; the iteration's timeout starts once a server-wide fault's iteration holds the server's lock, never while it waits for it), and one injector goroutine that schedules faults from the seeded generator and performs their clean-up. ## Lab resources

The fleet's containers are small (Alpine, about 30 MB of memory each): 35 per server fit easily in the standalone servers' 12 GiB. LXD's limit of 99 permissions per authorization group, not memory, bounds the fleet until gate L17. The cluster faults need one cluster at a time (3 × 4 GiB), as G-L16 did when both clusters exceeded the host's free memory. ST-6's VMs are small (384 MiB): the three of the evacuee and the baseline `v-ubuntu` (1 GiB) fit on the two members that receive them during an evacuation. A cycle takes a few minutes, each VM's disk crossing the network twice: about three hours per cluster with the defaults (three arms), plus about 8 minutes per blocked cycle (STR-74).
